# SupportFlow V1.7 制造运营助手第一版完成目标

状态：第一版核心链路已实现并通过自动化回归测试  
适用场景：永好塑胶制品（深圳）有限公司内部订单、生产、质检、库存协同演示  
数据性质：仓库内使用的是虚构/脱敏演示数据，不是公司真实生产数据库

## 1. 第一版目标

SupportFlow 从“退款审批演示”转为内部制造运营助手：

- 员工可以查询订单、物流、库存和生产进度。
- 员工可以提交客户订单、生产报工、质检报工和出库申请。
- 管理员可以在管理看板查看全局数据，并审批或驳回员工申请。
- 管理员可以直接创建订单，不需要再走员工申请审批。
- 生产、质检、出库的数量由后端使用可信订单和库存数据校验。
- LLM 只负责理解自然语言、补充缺失字段和组织查询结果；不直接修改数据库，也不授予权限。
- 员工报工支持“申请修改/申请撤回”，仍需管理员审批后才改变生产记录。
- 申请接口支持 `Idempotency-Key`，避免重复点击产生重复申请；待审批申请可以由本人撤回。

## 2. 业务主流程

### 员工提交订单

```text
员工填写客户编号、产品 SKU、需求数量、交期
  → 后端创建 SUBMITTED 申请
  → 管理员审核
  → 审核通过后创建 APPROVED 销售订单
  → 审核驳回只记录原因，不创建销售订单
```

### 员工报工和质检

```text
员工提交完成数量 / 合格数量 / 不良数量
  → 后端保存待审批申请
  → 管理员批准
  → 后端重新读取生产任务
  → 校验累计完成量不能超过计划量
  → 写入生产报工或质检记录
```

### 员工申请出库

```text
员工提交订单号和出库数量
  → 只创建 SUBMITTED 申请
  → 此时库存不变
  → 管理员批准
  → 后端重新读取订单和库存
  → 按库存批次扣减
  → 写入库存流水和物流事件
```

## 3. 角色和权限

### 员工默认权限

新注册员工可以立即登录，不会因为等待管理员授权而无法进入系统。默认包含：

- 查询订单、物流、库存、生产进度
- 提交客户订单
- 提交生产报工
- 提交质检报工
- 提交出库申请

默认权限只允许“提交申请”，不允许员工直接批准申请、直接改变库存或直接创建已批准订单。

### 管理员权限

管理员可以：

- 查看全体员工和修改权限
- 查看订单、申请、生产、质检、库存汇总
- 批准或驳回员工申请
- 直接创建已批准订单
- 继续使用系统原有的安全操作和审计能力

### 推荐角色模板

- `sales_employee`：业务员，查询订单/物流，提交客户订单。
- `production_employee`：生产员工，查询订单/生产，提交生产报工。
- `quality_employee`：质检员工，查询订单/生产，提交质检报工。
- `warehouse_employee`：仓库员工，查询订单/库存/物流，提交出库申请。
- `admin`：管理员，拥有全部权限和审批能力。

管理员可以在用户管理中选择角色模板后继续微调权限。旧的 `employee` 账号只有在仍保持系统原始默认权限时，才会被一次性补齐新的提交权限；已经被管理员定制过的账号不会被覆盖。

管理员账号仍由本地环境变量初始化。密码不会写入代码、镜像或文档。

## 4. 数据模型新增内容

第一版新增三个核心概念：

### `operation_requests`

统一记录员工提交的业务申请：

- `request_type`：订单、报工、质检、出库
- `status`：`SUBMITTED`、`APPROVED`、`REJECTED`、`FAILED`
- `requested_by`：申请人
- `payload_json`：申请内容快照
- `approved_by`：处理管理员
- `rejection_reason`：驳回或失败原因

### `quality_reports`

记录质检结果：

- 检验数量
- 合格数量
- 不合格数量
- 检验员
- 订单和日期

数据库约束保证：

```text
合格数量 + 不合格数量 = 检验数量
```

### `approval_records`

记录每次管理员批准或驳回，保留处理人、决定、原因和时间。

申请记录还支持 `WITHDRAWN` 状态和幂等键；报工记录支持通过审批变更或标记撤回，不会直接删除历史数据。

## 5. 后端接口

员工接口：

- `GET /operations/my-dashboard`
- `GET /operations/requests`
- `POST /operations/order-submissions`
- `POST /operations/production-reports`
- `POST /operations/quality-reports`
- `POST /operations/outbound-requests`
- `GET /operations/production-reports`
- `POST /operations/production-reports/{report_id}/change`
- `POST /operations/production-reports/{report_id}/withdraw`
- `POST /operations/requests/{request_id}/withdraw`

管理员接口：

- `GET /admin/operations/dashboard`
- `GET /admin/operations/requests`
- `POST /admin/operations/requests/{request_id}/decision`
- `POST /admin/operations/orders`

管理员看板支持按员工、申请状态和日期范围筛选，并返回员工报工/质检工作量、今日汇总和审批历史。

所有接口先经过登录和权限检查。前端隐藏按钮不是安全边界，后端会再次检查。

## 6. 数量和业务安全规则

- 数量必须是正整数、有限值，不能是负数、零、NaN、Infinity 或小数。
- 报工累计数量不能超过对应生产任务计划数量。
- 合格数量与不良数量不能超过完成数量。
- 质检数量不能超过已报工数量。
- 出库数量不能超过订单剩余数量。
- 出库批准前不修改库存。
- 出库批准时重新读取当前库存，库存不足则失败。
- 员工输入的“订单金额、库存、权限、审批状态”都不作为可信业务事实。
- 真正的订单、库存、生产任务和权限来自后端数据库。
- 每次申请和审批写入审计记录。

这套设计复用了之前退款流程中已经验证过的原则：申请和实际变更分离、后端二次校验、管理员确认、失败不产生副作用。

## 7. LLM 在第一版中的边界

LLM 可以帮助：

- 把“查一下 SF2002 现在做到多少了”理解成生产进度查询。
- 把“给 CUST-001 上 500 个 7 寸黑卷”整理成订单申请草稿。
- 发现缺少客户编号、订单号或数量时，用人话追问。
- 将数据库已经确认的结果整理成员工容易理解的回答。

LLM 不可以：

- 自己决定员工有没有权限。
- 自己批准订单、报工或出库。
- 自己修改库存、订单状态或生产数量。
- 把用户声称的数量当成数据库事实。
- 绕过管理员审批和后端数值校验。

因此，查询类问题可以直接由确定性查询返回；写入类问题必须经过后端申请和管理员审批。LLM 是“自然语言入口”，不是“数据库管理员”。

## 10. 当前明确限制

- 当前数据库是 SQLite，适合本地和小规模内部演示；多人长期使用前应迁移到 PostgreSQL 或公司已有数据库。
- 当前数据是虚构演示数据，需要由业务人员按实际字段和编码规则导入。
- 当前管理员审批是单级审批；如果实际业务需要部门主管、质检主管、仓库主管多级审批，应在下一阶段增加审批策略，而不是让 LLM 决定。
- 当前 LLM 仍主要服务于聊天入口；新的表单接口已经是确定性后端接口。
- 旧退款模块保留用于历史回归，尚未从仓库删除。

## 11. 下一阶段边界

在没有完成实际人工验收和字段确认前，不继续加入 Redis、Kafka、Kubernetes、微服务、多 Agent 或复杂 MES 功能。下一步优先级应是：

1. 用业务人员确认客户、产品、订单和库存字段。
2. 用几条脱敏真实流程做员工和管理员人工验收。
3. 确认审批角色和状态命名。
4. 再决定是否迁移数据库和增加生产环境部署。
